# 42 — Remaining gaps and their security implications

Nothing here is hidden by a green test run. Each gap says what an attacker or a failure could do.

| # | Gap | Security implication |
|---|---|---|
| 1 | **Write-ahead needs an attached store.** Signed output is released only after the `TrustStore` commit ([39](39-ANCHORED-RECOVERY.md)); a pipeline built without a store has no crash durability. | A host that never attaches a store loses `NoSelfEquivocation` across crashes (the `neg_nowal` failure). Hosts must attach one; `examples/edge-p2p` does and fails closed when it cannot open it. |
| 2 | **Formal results are bounded.** TLC completed models of up to 4 participants (n3: 3 players + 1 witness; n2_live: 2 players + 2 witnesses); a 5-participant model (`n5_exploratory`) did not finish and is not a result, one contested slot per signer, small value domains ([41](41-FORMAL-MODEL.md)). | No unbounded proof. Behaviours needing more slots, longer logs or more signers are covered only by tests. Cryptographic assumptions are outside the model. |
| 3 | **Hostile-network runs are finite.** Real-transport runs last minutes, not days; faults are injected at the witness-link layer above the real encrypted transport, not by an OS-level packet shaper ([40](40-WITNESS-NETWORK.md)). | Long-tail bugs (slow leaks, rare orderings) can remain. Transport-internal behaviour under kernel-level loss is not exercised. |
| 4 | **No third-party audit, no fuzzing campaign.** Decoders have bounded-length and mutation tests, not coverage-guided fuzzing. | A parser bug could crash or confuse a verifier. All decoders are length-checked before allocation and `forbid(unsafe_code)` is set in `gv-edge`. |
| 5 | **Cheat classes outside replay.** Aimbots producing legal inputs, wallhacks from information sent to a client, collusion. | Replay proves illegal transitions only. The arena is public-state, so there is no hidden information to leak, but a real game needs a visibility policy. |
| 6 | **1v1 stalls.** With one Byzantine opponent and no witness quorum the match cannot be forced to progress. | A timeout is `SUSPECTED_NONCOOPERATION`, never `PROVEN_FRAUD`. Games choose forfeit rules; the SDK proves no guilt from silence. |
| 7 | **Witness liveness is an assumption.** Convergence holds if at least one honest path exists between holders of evidence and each witness, and lost deliveries are retried (anti-entropy every ~1 s). | A permanently partitioned witness never learns the evidence; it is simply uninformed. Its verdicts, when it has evidence, are still correct, because they depend on signatures and replay only. |
| 8 | **Witness admission is pinned, not open.** Players must know each witness key in advance; there is no discovery or Sybil resistance. | A player cannot be forced to talk to unknown witnesses, so witness count is not a security parameter; a verdict never depends on it. |
| 9 | **Evidence retention is bounded.** Witnesses keep at most `MAX_ITEMS` (1024) items and 256 authenticators per owner; players prune logs. | Under a flood of *valid* distinct evidence older items can be evicted. Anyone holding a package can still verify it offline. |
| 10 | **Platform coverage.** Linux x86-64 and Windows x86-64 run the full suite, including the kill-at-every-boundary durability tests; macOS is not exercised. Windows directory sync opens the directory with `FILE_FLAG_BACKUP_SEMANTICS` (`audit/fsync.rs`); before that fix every Windows commit failed, so the write-ahead barrier withheld all signed output. | On macOS, `fsync` does not force data to stable media (`F_FULLFSYNC` does), so a power loss could undo a commit the barrier treated as durable. NTFS renames are journalled, but write-through on the rename itself is not requested. |
| 11 | **Hydra identity files are protected by a password-derived key.** | Local secret management is the deployer's responsibility; the SDK never exports secret keys or Hydra session state. |
| 12 | **Machine stability.** The development machine rebooted several times while heavy jobs ran. The cause was not established. | Heavy checks are run one at a time at low priority, with bounded resources. A reader reproducing them should do the same. |

**Transport identity (audited).** `p2p-net` builds on libp2p, whose peer identities and `Cargo.lock` include Ed25519 (`libp2p-identity`). Audit of every use of `PeerId` in this repository: it appears only in `adapters/p2p/src/native.rs` (dialing, and filtering inbound pub/sub messages by `source_peer_id` so the session reads only its chosen peer). It never reaches `crates/edge`, the audit/evidence/feed/archive code, or the witness protocol, none of which accept a `PeerId` as an input to any authentication or verdict. Gameplay frames are authenticated by the Hydra ML-DSA-65 handshake and per-packet keys; accountability messages, authenticators, evidence and feed events carry ML-DSA-65 signatures over their own bytes. Consequences: a forged or hijacked `PeerId` can at most cause messages to be dropped or misrouted (availability), cannot make a forged message verify, and cannot create or hide fraud evidence. Residual: the transport's Ed25519 identity is not post-quantum, so a quantum adversary could impersonate a peer at the transport layer (traffic analysis, selective denial of service, eclipsing); it still could not forge any signed protocol artifact. Peer-identity-to-player binding is deliberately not established by libp2p.
