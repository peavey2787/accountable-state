# 13 — Optional general-purpose Groth16 / zkVM backend

## Principle

The standard verification path is **cryptographic commitments + independently repeatable deterministic replay**. Zero knowledge is only necessary when public replay would disclose secrets beyond the game's allowed visibility model, when evidence costs exceed acceptable bounds, or when an external verifier must check a succinct statement. It MUST remain an optional backend.

## Preferred generic architecture

A Rust-compatible zkVM can execute a **pinned game verifier** as a guest; a reusable proof wrapper attests to the guest program identity and public journal. RISC Zero's Groth16 compression is a plausible interoperability target for an external proof verifier. Different games plug in separately pinned verifier programs/guest inputs; no need to hand-author a different pairing verifier for each game. **This does not mean all Rust gameplay automatically runs efficiently in a zkVM.** Cost, determinism, memory and supported syscalls need evaluation per title.

## Proof statement for fraudulent transition

Public claim MUST bind:

```text
protocol_version
match_id, chain/network domain (if relevant)
accepted_checkpoint_id, parent/root and match manifest hash
canonical_ruleset_hash, canonical_game_verifier_image_id
accepted_old_state_commitment, claimed_next_state_commitment
input_batch_commitment, authenticated authorization/ordering context
fraud_predicate_id and deterministic verdict code
proof_system_tag + verification_key / program identity
```

Private witness MAY include exact old/new state openings, Merkle authentication paths, authorized input batch, game randomness, collision/map data, full prior snapshot and proof of deterministic invalidity. The guest checks the accepted root/QC or proves the link to a externally authenticated value, reconstructs the correct transition under the pinned rules, and asserts a precise contradiction with the accepted claim. A circuit that only proves an arbitrary speed bound or arbitrary claimed root without accepted history is unsound for anti-cheat. Domain-separate any public digest expected by the on-chain contract.

## Verify versus prove

`verify(proof, public_claim, trusted_verifier_id) == true` certifies the pinned statement if the proof system is sound, verification key is correct, and the guest relation faithfully expresses the official rules. **It does not attest player intent, unbiased game state publication, legal human actions, availability of off-chain witness, or acceptance by a particular match unless those facts are cryptographically linked inside the statement.** Implement independent positive/negative fixture tests for the relation and its chain verifier.

## Groth16 considerations

Groth16 over BN254 is succinct for external checking, but not post-quantum secure and may use a trusted setup depending on prover architecture. Recursive zkVM compression and trusted setup provenance should be public and reproducible. RISC Zero guest/image ID and journal binding must match the verifier's exact receipt encoding. Prevent substitution of a weaker verifier, proof-system tag or circuit. Pin compiler toolchain, guest ELF, image ID, verifying key artifacts, setup ceremony parameters and version.

## Resource budget

ZK guest execution in gameplay is likely much more expensive than signature verification/replay. Never require 60 proofs per second without measurement. Prefer post-match, batched, or dispute-only proof generation; benchmark proving wall time, RAM/VRAM, proof bytes, verification latency  and external-verifier script compute budget on commodity target devices, including browsers and integrated GPUs. Provide a non-ZK reference mode where disclosure is permitted.

## Current implementation boundary

`gv-zk-private` is a working backend for never-reveal state, built on the zk-sdk predicate engine (KoalaBear, Spartan-WHIR, full zero knowledge, no trusted setup, pinned by git revision). A `Program` pins the transition rules (compare, add, sub, require, ensure, conserve) and a violation code; its id commits to both. `advance` moves a hidden `State` to a new one and returns the `PublicClaim` and proof; `PrivateTransitionVerifier` implements `ZkVerifier`. The proof reveals only the two commitment lists. The claim's `prior_root` and `next_root` must be digests of those lists, and the last field of the new state is proven equal to a 128-bit tag over the program, match, manifest, ruleset, checkpoint and input root, so a proof cannot be reused for another claim. Steps chain by state root. Limits: at most seven rules per program, rules come from the fixed vocabulary above, nothing here stops a prover replaying a step or branching one state into two (the match ledger and signed checkpoints do that), and proving is far too slow for per-tick use: use it post-match or for disputes. `gv-zk::DisabledZk` remains the default and rejects all proofs with `Unsupported`. It intentionally does **not** accept unvalidated proof blobs. Production conformance requires pinned RISC Zero guest build, Groth16 compression, a chosen proof-verification target, independent verifier vectors, fuzzing and economic limits. No on-chain cheat proof is generated by this skeleton.

## r3 signed event batching / independent 1v1 evidence

Event packing is independent of ZK. In public challenges replay the admissible packed witness; if publication would expose forbidden data, prove the pinned verification relation with a suitable Groth16/zkVM backend instead. Chain-verified proofs must bind to admitted canonical transcript root, signed claim and ruleset; a digest alone is not a ZK fraud proof. See [r3](22-INPUT-PACKING-AND-DECENTRALIZED-1V1.md).
